# Low-context documentation maintenance

## Objective

ChrisOS documentation is designed to grow without requiring every maintenance task to reload the whole corpus or the whole source repository into one reasoning context.

The maintenance model therefore separates three kinds of information:

1. deterministic repository facts generated by scripts;
2. narrow source context selected by explicit metadata;
3. authored technical interpretation that requires engineering judgment.

The core goal is not merely to reduce token usage. It is to make documentation maintenance **bounded, reproducible and reviewable**.

A page should normally be maintainable from itself, its declared source dependencies, the relevant Git diff and a small set of prerequisite headings.

## Why low-context maintenance matters

A large technical corpus creates two failure modes if every update begins with a full-repository reread.

First, cost grows with total repository size even when a one-line driver change affects only one chapter.

Second, broad context makes it easier to mix unrelated assumptions and harder to prove why a page was changed.

ChrisOS avoids this by storing explicit dependency metadata in frontmatter and generating deterministic impact maps.

The intended maintenance unit is:

    one target page
      + declared source paths
      + changed-source diff
      + selected dependency context
      + validation evidence

not:

    entire source tree
      + entire documentation tree
      + semantic guessing

## Canonical page identity

Maintenance operates on frontmatter `id`, not filename similarity.

A page can move to a different route while preserving its semantic identity.

The bilingual pair is identified by:

    (id, en)
    (id, pt-br)

This is important because the maintenance system must not create duplicate pages merely because a filename differs from a manifest ID.

The documentation schema defines the complete identity rules.

## Frontmatter dependency graph

The primary maintenance metadata fields are:

- `sources`;
- `symbols`;
- `depends_on`;
- `related`;
- `reviewed_revision`.

Together they create a graph from implementation to authored explanation.

Conceptually:

    ChrisOS source file
          |
          v
       sources
          |
          v
    documentation page
       /          \
      v            v
 depends_on      related

A change to one source path can therefore be mapped deterministically to the pages that declared it.

No semantic search is required for the first impact pass.

## sources

`sources` is the authoritative implementation dependency list for source-diff maintenance.

Each entry is a path relative to the ChrisOS source repository.

A page should declare the smallest useful set of files needed to reconstruct its implementation claims.

Too few sources can hide an important change from stale detection.

Too many sources create noisy review queues and force unnecessary reconciliation.

The goal is not exhaustive transitive dependency capture; it is accurate documentation dependency capture.

## symbols

`symbols` narrows large source files to the identifiers most useful for review.

A context pack can use these identifiers to extract focused source windows rather than sending an entire large implementation file.

Symbols are hints.

They do not replace source dependencies, and they should not be treated as stable ABI merely because they appear in frontmatter.

## depends_on

`depends_on` records prerequisite knowledge.

It supports:

- curriculum ordering;
- DAG validation;
- bounded prerequisite context;
- reviewer orientation.

A maintenance agent should not automatically rewrite prerequisite pages just because a dependent page changed.

The dependency is conceptual, not reverse ownership.

## related

`related` provides navigation between adjacent topics that are not strict prerequisites.

Typical relationships include:

- implementation and specification;
- subsystem and validation;
- current architecture and history;
- alternative backend.

Related pages can help a reviewer understand scope, but they are not automatically part of every context pack.

## reviewed_revision

`reviewed_revision` records the ChrisOS source revision against which the page was last reconciled.

It is the baseline for stale detection.

It must not be advanced simply because the page was opened or because a workflow needs to become green.

The field means:

> this page was deliberately checked against this source revision.

Updating it without review destroys the dependency-tracking model.

## Reverse source map

`source_map.py` builds a reverse mapping from source path to documentation pages.

The output answers:

> Which authored pages declare this changed source file?

This is much cheaper and more reliable than searching the corpus for words that happen to resemble a filename or subsystem name.

The source map is deterministic because it is generated from frontmatter.

If the map is wrong, the metadata should be fixed rather than adding model heuristics.

## Stale detection

`stale_docs.py` compares each implementation-facing page from its `reviewed_revision` to current ChrisOS HEAD, but only across its declared `sources`.

Conceptually:

    git diff reviewed_revision..HEAD -- declared/source/path ...

If no declared source changed, unrelated repository activity does not make the page stale.

If a declared source changed, the page enters the generated review queue.

This makes maintenance scale with **affected documentation**, not with total repository size.

## What stale means

A stale page means:

> at least one declared source dependency changed after the page's reviewed baseline.

It does not mean:

> the prose is definitely wrong.

Many changes are implementation-only or editorial.

The reviewer must inspect the diff and determine whether the page's contract, examples, limitations, ownership or validation claims changed.

If the prose remains correct, advancing `reviewed_revision` after inspection is a legitimate reconciliation.

## Unavailable baselines

A historical reviewed revision may occasionally be unavailable in a shallow checkout or pruned environment.

The maintenance tooling must classify this as an unavailable baseline, not as an empty diff.

No diff is not evidence of no change when the baseline itself cannot be resolved.

The correct response is to obtain enough Git history or perform a full reconciliation against current source.

## Generated review queue

The review queue is an attention list built from stale detection.

A useful queue entry identifies:

- page;
- language;
- reviewed revision;
- changed declared sources.

The queue is generated state.

It should not be manually edited to hide work.

To remove an entry, either reconcile the page and update its revision or correct inaccurate source metadata.

## Context packs

`context_pack.py` creates bounded review material for one target page.

A context pack can contain:

- target page;
- metadata;
- declared source content;
- symbol-centered excerpts;
- Git diff since reviewed revision;
- source hashes;
- prerequisite headings;
- concise maintenance instructions.

The context pack is intended to be sufficient for an agent to answer:

1. what did the page previously claim?
2. what source changed?
3. what is the current implementation?
4. which claims need revision?
5. which claims remain valid?

## Context-pack size discipline

More context is not automatically better.

A context pack should expand only when the current packet cannot resolve a material question.

Typical escalation order:

1. target page;
2. declared symbol window;
3. full declared file;
4. direct caller/callee source;
5. relevant test;
6. historical commit;
7. broader subsystem search.

This prevents repository-wide exploration for every maintenance event.

## Generated facts

Scripts can generate facts that do not require model interpretation.

Examples include:

- path;
- hash;
- line count;
- include graph;
- detected symbol names;
- manifest membership;
- bilingual presence;
- word counts;
- source-to-page mapping.

These facts should be generated deterministically.

An agent should not spend reasoning budget reconstructing them from prose when the repository can calculate them exactly.

## Source atlas

The generated source atlas mirrors/indexes source material for navigation and retrieval.

Its purpose is exact source access, not authored interpretation.

The atlas should not be manually rewritten into summaries.

If the source changes, regenerate the atlas from the source checkout.

This keeps generated facts mechanically synchronized with implementation.

## Authored interpretation

Some documentation properties cannot be generated reliably from syntax alone.

Authored pages remain responsible for:

- architecture;
- invariants;
- ownership;
- lifetime;
- concurrency;
- ABI meaning;
- error propagation;
- recovery;
- rationale;
- performance implications;
- security boundaries;
- validation interpretation;
- limitations.

These are the areas where engineering reasoning is required.

A generated symbol list can say that a lock exists.

It cannot reliably establish whether the lock protects ownership, ordering or merely statistics.

## Generated versus authored ownership

Every artifact should have one clear owner.

| Artifact | Owner |
|---|---|
| implementation code | ChrisOS source repository |
| frontmatter metadata | authored documentation |
| technical prose | authored documentation |
| manifest/curriculum | curated data |
| source map | generator |
| source atlas | generator |
| review queue | generator |
| coverage report | generator |
| static site output | build pipeline |

Editing a generated file by hand is usually the wrong layer.

Fix its input or generator instead.

## Selecting the next maintenance task

Once structural coverage is complete, work should come from generated maintenance signals rather than inventing new chapters.

A useful priority order is:

1. invalid source/revision metadata;
2. stale pages affecting current capability claims;
3. pages below editorial depth floor;
4. broken curriculum or navigation;
5. unresolved specification/implementation mismatch;
6. broader quality improvements.

This keeps maintenance tied to measurable corpus state.

## Structural coverage versus depth

Structural coverage asks:

> does the planned bilingual chapter exist?

Depth asks:

> is the authored chapter substantial enough for its role?

These are separate signals.

A corpus can be 100% structurally complete while still containing shallow pages.

The completion campaign should therefore continue after the final manifest ID exists, using the generated depth backlog as the next work queue.

## Word-floor policy

Word floors are guardrails, not proof of quality.

A page below its target is a signal to inspect whether important dimensions are missing.

Useful expansion dimensions include:

- initialization;
- ownership;
- memory;
- algorithms;
- concurrency;
- error paths;
- validation;
- limitations;
- security;
- performance;
- compatibility.

Do not add filler merely to cross a numeric threshold.

Every expansion should close a technical gap.

## Bilingual maintenance

EN and PT-BR pages with the same ID must remain technically equivalent.

The maintenance workflow should preserve equal:

- source dependencies;
- prerequisite graph;
- reviewed revision.

The prose does not have to be sentence-for-sentence translation.

Both languages should independently communicate the same technical contract and limitations.

When a substantive change affects one language, the paired page should normally be updated in the same maintenance batch.

## Intermediate CI failures

Bilingual validation can make an intermediate EN-only commit fail because the paired PT-BR page is temporarily inconsistent.

The meaningful validation target is the final commit containing both halves of the change.

Intermediate pair-incomplete failure is not necessarily a content regression.

However, the final bilingual commit must pass the full workflow before the batch is considered complete.

## Reconciliation workflow

A normal stale-page reconciliation proceeds as follows:

1. read the target page;
2. inspect frontmatter sources and symbols;
3. inspect the source diff since `reviewed_revision`;
4. inspect current source;
5. inspect relevant tests/specifications;
6. classify each affected claim;
7. update prose only where the contract changed;
8. preserve limitations;
9. update both languages;
10. advance `reviewed_revision`;
11. run the documentation pipeline;
12. confirm the page disappears from the stale queue.

This workflow avoids both unnecessary rewriting and blind revision bumps.

## Claim classification during review

For each potentially affected statement, classify it as:

- unchanged;
- implementation detail changed;
- contract changed;
- evidence improved;
- limitation removed;
- new limitation introduced;
- historical only;
- roadmap only.

This forces the reviewer to distinguish source churn from documentation-relevant change.

## Validation of documentation changes

The core local publication sequence is:

    python -m unittest discover -s tests
    python scripts/build_all.py --source .source --docs docs
    mkdocs build --strict

The hosted workflow adds additional:

- contract verifiers;
- source-fact checks;
- JavaScript checks;
- SEO/discovery checks;
- reader smoke tests;
- Pages artifact validation.

A maintenance batch is not complete merely because Markdown renders locally.

## Documentation CI is not runtime CI

A green documentation workflow proves properties of the documentation repository:

- metadata valid;
- source paths resolvable;
- curriculum valid;
- generated artifacts build;
- site compiles;
- reader checks pass.

It does not prove that the ChrisOS kernel boots or that a driver works.

Runtime claims still require ChrisOS tests and gates.

This distinction must remain explicit during agent maintenance.

## Source revision updates

If review finds no semantic prose change, it can still be correct to update only `reviewed_revision`.

That update should occur only after the relevant diff was inspected.

The commit message should make the reconciliation intent clear so future history does not look like an unexplained metadata churn.

## Adding source dependencies

During review, the agent may discover that a page depends on a source file that was not declared.

Add it when the file materially supports a current implementation claim.

After adding it, stale detection will begin tracking that dependency for future revisions.

Do not add unrelated files only to make a context pack larger.

## Removing source dependencies

Remove a source path when the page no longer depends on it.

This commonly occurs after:

- subsystem refactoring;
- ownership transfer;
- API extraction;
- historical content moving to a history chapter.

Keeping obsolete dependencies creates recurring stale noise.

## Historical pages

History pages use revision evidence differently from current implementation pages.

They may cite old commits because change over time is their subject.

A historical commit referenced in prose should not be automatically replaced with current HEAD.

Only the frontmatter reviewed baseline should track the current source state used to reconcile the history page as a whole.

## Specifications

Specification pages need special care.

A source change can be implementation-only or it can alter a persistent/ABI contract.

The reviewer should inspect:

- magic/version;
- field layout;
- bounds;
- reader acceptance;
- writer output;
- compatibility;
- migration;
- error semantics.

A specification should never be updated from a struct diff alone without determining whether serialized behavior changed.

## Validation pages

Validation documentation also needs source reconciliation when gate definitions change.

A new gate dependency, marker, timeout rule or skip behavior changes what the project can claim even when kernel source is unchanged.

Therefore makefiles and test harnesses can legitimately be declared sources for validation chapters.

## Developer guides

Operational guides should remain close to exact repository commands.

When build or setup commands change, source-repository operational docs and canonical site guides may both need updates.

The maintenance agent should distinguish:

- repository-local command truth;
- long-form architectural explanation.

Duplicated commands should be minimized where possible, but operational accuracy has priority.

## Failure handling during maintenance

If a documentation build fails, classify the failure before editing prose.

Common categories include:

- bilingual mismatch;
- invalid source path;
- duplicate ID;
- curriculum cycle;
- generated artifact drift;
- static-site warning promoted to error;
- reader/JavaScript regression;
- unrelated infrastructure failure.

Fix the actual failing layer.

Do not change technical content merely to silence an infrastructure error.

## Preserving first failure evidence

When CI fails, preserve the first meaningful error and the commit that produced it.

Repeated commits can cancel prior workflows or overwrite generated artifacts.

A concise failure record helps distinguish:

- expected intermediate bilingual failure;
- real final-content regression;
- environment/infrastructure failure.

This principle mirrors ChrisOS runtime validation discipline.

## Cost-control rules

The low-context model uses several cost controls:

1. cache unchanged source by Git content identity;
2. use explicit dependency metadata;
3. review diffs before full files;
4. expand context only when material uncertainty remains;
5. generate repository facts without a model;
6. do not regenerate unaffected prose;
7. preserve reviewed revisions as stable baselines;
8. use deterministic queues instead of broad semantic rediscovery.

These rules reduce both computation and accidental editorial churn.

## Scaling property

Let:

- (D) be total documentation size;
- (S) total source size;
- (A) source paths affected by a change;
- (P) pages declaring those paths.

A naive maintenance strategy tends toward work proportional to:

    O(D + S)

The intended metadata-driven strategy is closer to:

    O(A + P)

plus the bounded source context needed to resolve those pages.

This is the main reason the model can scale to a much larger corpus.

## Human and agent roles

Automation and agents should complement each other.

Deterministic scripts own:

- indexing;
- counting;
- hashing;
- graph checks;
- stale detection;
- source extraction.

Engineering review owns:

- meaning;
- architectural boundaries;
- trade-offs;
- evidence interpretation;
- compatibility;
- limitations.

A good workflow does not ask a language model to perform work the repository can calculate exactly.

## Completion criteria for a maintenance batch

A maintenance batch is complete when:

1. targeted pages are technically reconciled;
2. EN/PT-BR remain equivalent;
3. frontmatter is correct;
4. reviewed revision is truthful;
5. generated queues reflect the new state;
6. depth warnings addressed by the batch are actually removed;
7. full documentation CI passes;
8. Pages/static artifact is produced successfully.

This creates an auditable endpoint.
